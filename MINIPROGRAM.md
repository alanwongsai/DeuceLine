## Settled decisions (Alan, 2026-09-24)

| Decision | Choice | Consequence for the port |
|---|---|---|
| Source of truth | **GitHub repo JSON stays canonical** (`public/data/deuceline-data.json`) | No CloudBase database. Cloud functions read/commit the repo file through the GitHub API. |
| Mini program write auth | **Same shared password** as the web (`ADD_MATCH_PASSWORD`) | Alan is the only editor. Same gate code as the web (`checkPublishKey`). |
| Distribution | **体验版 (trial version) only** | No review/上架 for now; add Andy as an experience member. |
| Visual fidelity | **Keep the essence, not a 1:1 copy** | Follow "Design essence" below; simplification is expected where WXML/WXSS differ. |
| Code location | **Same repo, maintained in parallel** | `miniprogram/` + `cloudfunctions/` + root `project.config.json`. |

Non-negotiable: **the web/PWA path keeps running unchanged.** The port adds folders; it does
not edit `src/`, `functions/`, `public/` or the Cloudflare setup (except through a normal,
reviewed change that keeps `npm run typecheck && npm test && npm run build` green).

## Architecture (dual track, one truth)

```text
                GitHub: public/data/deuceline-data.json   ← single source of truth
                  ▲ commit (PAT)                     ▲ commit (PAT)
  Cloudflare Pages Functions                   CloudBase cloud functions
  functions/api/add-match.ts, update-match.ts  cloudfunctions/getDataset, addMatch, updateMatch
                  ▲ fetch /api/*                     ▲ wx.cloud.callFunction
        Web PWA (React, src/)                  Mini program (WXML/WXSS, miniprogram/)
                  │                                  │
                  └─────── same rules, same code ────┘
     src/domain (validate · derive · add/replace)   +   functions/api/_publish.ts (write gate + rules)
```

- **Reads.** The web fetches the static JSON. The mini program calls the `getDataset` cloud
  function, which reads the file through the GitHub Contents API — so the mini program needs
  **no request-domain whitelist and no ICP filing**; every network call is a cloud function.
- **Writes.** Both hosts run the identical publish core: password gate → append-only add, or
  update only while the *stored* match is unfinished → server-side re-validation → one commit.
  A commit to `main` also redeploys the web on Cloudflare, so both clients converge.
- **Freshness.** The mini program reads GitHub directly, so it sees a new match immediately;
  the web sees it after the Cloudflare redeploy (about a minute).

## The shared core — `npm run build:core`

`scripts/build-core.mjs` bundles the TypeScript sources into plain CommonJS `.js` (ES2018
syntax, the only module format both the mini program and Node cloud functions load without
extra tooling), writes them to `dist-core/` (git-ignored), also emits the default skin tokens
as WXSS and the app version as a CommonJS module, self-checks the domain bundle against
the real dataset, and **copies them into `miniprogram/lib/` and every `cloudfunctions/*/lib/`
when those folders exist.**

Rule: **whenever `src/domain/`, `functions/api/_publish.ts`, `functions/api/_github.ts` or
`src/styles/skins.css` changes, run `npm run build:core` and commit the refreshed copies in the
same change.** The mini program must never re-implement validation, derivation, scoring or the
write rules — if it needs a new derived figure, add a pure function to `src/domain/` (with a
test) and rebuild.

What the bundles expose:

| Bundle | Main exports |
|---|---|
| `deuceline-domain.js` | `validateDataset`, `DatasetValidationError`, `deriveOverviewStats`, `sortMatchesNewestFirst`, `isUnfinished`, `deriveMatchResult`, `formatWinnerScoreline`, `formatNeutralScoreline`, `formatSetScore`, `deriveMatchContext`, `deriveTimeline`, `deriveCadence(matches, now)`, `deriveDataCoverage`, `deriveGamesTally`, `matchGamesTally`, `deriveScorelineDistribution`, `longestRun`, `maxLead`, `deriveSurfaceForm`, `appendMatch`, `replaceMatch`, `serializeDataset`, `SURFACES`, `WEATHER_TAGS` |
| `deuceline-publisher.js` | `checkPublishKey(config, key)`, `handleGetDataset(store)`, `handleAddMatch(store, body)`, `handleUpdateMatch(store, body)`, `createGitHubStore(token)`, `PublishError` |
| `deuceline-version.js` | `version` — from `package.json`, so the cover badge has no second copy to drift |

Every handler returns `{ status, body }` with the same statuses and messages as the web
endpoints (200 · 400 bad body · 401 wrong password · 404 unknown id · 409 data changed, reload ·
422 rejected with `issues` · 500 not configured · 502 GitHub/unexpected failure). On success
`body.dataset` is the full next dataset — refresh the UI from it, don't re-fetch.

### Cloud functions (complete reference implementations)

Runtime **Node.js 18 or newer** (the store relies on global `fetch`/`btoa`/`TextEncoder`). No
`wx-server-sdk` or database is needed. Configure per function in the CloudBase console:

- Environment variables: `GITHUB_TOKEN` (fine-grained PAT, this repo only, Contents read/write —
  preferably a **separate** PAT from the Cloudflare one so each can be revoked alone) and
  `ADD_MATCH_PASSWORD` (the **same** value as on Cloudflare). `getDataset` needs only the token.
- Timeout: raise the default to ~20 s; a publish is one GitHub read plus one commit.

```js
// cloudfunctions/getDataset/index.js
const { createGitHubStore, handleGetDataset } = require("./lib/deuceline-publisher.js");
exports.main = async () => {
  if (!process.env.GITHUB_TOKEN) return { status: 500, body: { error: "Publisher is not configured." } };
  return handleGetDataset(createGitHubStore(process.env.GITHUB_TOKEN));
};

// cloudfunctions/addMatch/index.js
const { checkPublishKey, createGitHubStore, handleAddMatch } = require("./lib/deuceline-publisher.js");
exports.main = async (event) => {
  const denied = checkPublishKey(process.env, event.key);
  if (denied) return denied;
  return handleAddMatch(createGitHubStore(process.env.GITHUB_TOKEN), { match: event.match });
};

// cloudfunctions/updateMatch/index.js
const { checkPublishKey, createGitHubStore, handleUpdateMatch } = require("./lib/deuceline-publisher.js");
exports.main = async (event) => {
  const denied = checkPublishKey(process.env, event.key);
  if (denied) return denied;
  return handleUpdateMatch(createGitHubStore(process.env.GITHUB_TOKEN), { id: event.id, match: event.match });
};
```

### Mini program data flow (mirror of the web)

```js
const domain = require("../../lib/deuceline-domain.js");

// Load: cloud function → validate again on the client (the web validates every read too).
const { result } = await wx.cloud.callFunction({ name: "getDataset" });
if (result.status !== 200) { /* show result.body.error + a Reload button */ }
const dataset = domain.validateDataset(result.body.dataset);
const stats = domain.deriveOverviewStats(dataset.matches);

// Publish: build input → appendMatch/replaceMatch + validateDataset locally for the review
// step → callFunction("addMatch" | "updateMatch", { key, match[, id] }) → on 200 replace
// state with domain.validateDataset(result.body.dataset).
```

- The password is kept with `wx.setStorageSync("deuceline.addMatchKey", …)` after a successful
  publish and cleared on a 401 — the same device-only behaviour as the web's `localStorage`.
- The last good dataset may be cached in storage as an **offline fallback only** (like the web
  service worker). It is never canonical and never written back.
- A failed load or validation must be shown clearly with a **Reload data** action, with raw
  issues collapsible — never silently render partial data.

## What to port by hand (small, presentation-only)

These live in React files, not the domain, and are cheap to re-create in `miniprogram/utils/`:
`shortDate` (en-GB `02 Sep 2026`), `numberWord`, `formatPercentagePair` and narrative
presentation in `src/pages/OverviewPage.tsx` (the derived narrative itself lives in the
shared domain); surface/weather labels in
`src/components/SurfaceBadge.tsx` and `src/components/weather.tsx`; sheet copy in
`src/components/OverviewSheets.tsx`. Keep the UI copy in **English**, as on the web.

Web-only pieces to **drop**, not port: service worker / manifest, the clipboard + GitHub-editor
fallback in `AddMatchSheet` (the mini program cannot open github.com; on failure it shows the
error and lets you retry), the `data-skin` attribute switching, and the DOM focus-trap / scroll-lock
code in `Modal.tsx` (use `page-container` or a fixed half-screen view instead).

## Design direction (target for the future client)

The current mini program is only a native shell with Overview and Matches placeholders.
This section describes the design target for the future full client; it does not imply
that the data views, evidence sheets, add/update flow, or publishing experience are
implemented. The full client and its 体验版 release remain a future phase in
[PROJECT_PLAN.md](PROJECT_PLAN.md) (Phase 12).

The design uses a quiet **court-inspired canvas, translucent glass controls, and serif
chapter typography**. The leather cover, paper texture, crest, and stamp are retired from
the mini program. Keep, in priority order:

1. **Identity colour, never win/loss colour.** Every player cue (identity dots, underlines, stripes,
   chart markers and recent form) uses `players.alan.color` /
   `players.opponent.color` and `abbr` **from the dataset** — never hard-coded, never red/green
   for lose/win.
2. **Materials and visual hierarchy.** Use generated Wimbledon skin tokens from
   `lib/deuceline-tokens.wxss`: `--base`, `--wash`, `--ink`, `--muted`, `--court`,
   `--content`, `--glass`, and `--rim`. Keep the page canvas calm and legible; reserve
   translucent glass for floating controls and badges, with a solid `--sheet` fallback
   where blur is unsupported. Use serif type for the rivalry score and chapter headings.
   The shared header is a restrained title row with a compact version/count badge; it has
   no leather band, paper grain, crest, or stamp.
3. **The head-to-head is the anchor.** Player names carry data-owned identity dots, then
   huge neutral serif match tallies (tabular), a `HEAD-TO-HEAD` label and a finished-match /
   win-rate meta line. Tapping it opens the rivalry story sheet. Identity text at night
   needs a readable neutral foreground with the original hue retained as a marker.
4. **Voice.** A short plain-language note summarises the state; matches are **chapters** with a
   chapter number and a dot in the winner's colour; scorelines read from the **winner's side** ("Andy won
   2—1", sets winner-first) via `formatWinnerScoreline`.
5. **Evidence honesty.** The 2×2 *Rivalry ledger* (Set record · Deciders · Set 1 → win · Current
   run) — each cell opens its evidence sheet; every row says **Full set scores** vs **Score
   summary**; the footer shows data coverage (dates / set scores / weather out of finished).
   Unfinished matches: split two-colour stripe, "In progress", excluded from every stat.
6. **Information architecture.** Overview = state now (H2H, ledger, latest chapter expanded,
   Form / Surfaces / Timeline lenses, two recent chapter rows, "View all"). Matches = the
   complete archive (its own title row, surface filter chips with counts, every match incl.
   unfinished). Centre Add = record or complete one match. Tab bar: Overview · (+) · Matches,
   with the (+) using the shared court/accent material.
7. **Surface badges** are explicitly labelled neutral pills. Surface category and theme
   must not imply a player identity colour.

Free to simplify:

- **Assets.** The current mini shell needs no journal artwork. Keep its package free of the old
  crest and stamp; use CSS/WXSS materials and the generated skin tokens. Heroicons SVGs
  (`public/assets/icons/`) can be used via `<image>` when a future screen needs them.
- **Fonts.** Georgia / Baskerville exist on iOS; on Android accept the system `serif`
  fallback. Don't ship web fonts for this.
- **Charts.** The lead sparkline / timeline are inline SVG on the web, which WXML lacks. Draw
  them with `<canvas type="2d">` or an SVG string as an `<image>` data URI; the interactive
  scrubber can come later (a `<slider>` is the native equivalent of the web range control).
- **Motion.** Count-up and sheet transitions are optional; respect reduced motion if added.
- The exact web chrome tokens are available as CSS variables from `lib/deuceline-tokens.wxss`.
  The current build extracts only the default Wimbledon block; web skin/evening overrides
  are not exported, including web player-display overrides. The existing mini skeleton
  continues to use dataset identity colours; full runtime appearance switching in the mini
  client is future port work. Web palette resolution is documented in ENGINE.md.

## Acceptance checklist

- [ ] Web unchanged: `npm run typecheck && npm test && npm run build` pass; the live site behaves as before.
- [ ] `npm run build:core` passes and the committed `miniprogram/lib/` + `cloudfunctions/*/lib/`
      copies match it (re-running it produces no diff).
- [ ] No validation/derivation/scoring logic outside `src/domain` (grep the mini program for scoring math).
- [ ] Mini program Overview shows the same H2H, ledger and latest chapter as the web.
- [ ] A match added from the mini program appears there immediately and on the web after redeploy; and vice versa.
- [ ] Wrong password → "Wrong password." and the stored key is cleared; a finished match cannot be updated.
- [ ] Player colours come from the dataset; changing them in the JSON recolours both clients.
- [ ] Main package under 2 MB; no secret (token, password) in any committed file.
